# Release notes — v0.23.1 — the v0.23.0 upgrade migration repair

**Version badge after updating:** `v0.23.1 · pre-release`.

## What happened

v0.23.0 is broken for every installation that upgraded to it from v0.20.0–v0.22.1. On update the
container logged `[migrate] database is up to date`, the server started, and every page that reads
the pots table then failed with:

```text
SqliteError: no such column: "credit_card_payment_day_of_month"
```

No data was lost or corrupted: the five credit-card columns simply never got added, so queries
referencing them fail. Fresh installs (empty `/data`) were unaffected — which is why CI, the Docker
smoke test and the browser suite were all green on v0.23.0. Only the upgrade path was broken, and
nothing ever tested it.

## Root cause

drizzle's SQLite migrator decides what to apply by comparing each journal entry's `when` stamp
against **only the newest `created_at` recorded in the database's `__drizzle_migrations` table**
(it selects `ORDER BY created_at DESC LIMIT 1`). An entry stamped earlier than an already-recorded
entry is silently skipped; fresh databases, which have no rows yet, apply everything in order.

`drizzle/meta/_journal.json` shipped:

| journal entry | `when` stamp | origin |
|---|---|---|
| `0011_schedule_excluded_months` | `1790600000000` (2026-09-28 13:06 UTC) | hand-stamped round number, **in the future** |
| `0012_credit_card_pots` | `1790506141836` (2026-09-27 10:49 UTC) | real generation time |

0012's real stamp is numerically smaller than 0011's hand-stamped one, so every database that had
0011 recorded — any install upgraded from v0.20.0 or later — silently skipped 0012 when updating
to v0.23.0.

## The fix

1. **Journal entry 0011 is re-dated to `1790504000000`**, restoring strictly increasing,
   never-future stamps: 0010 (`1790500000000`) < 0011 (`1790504000000`) < 0012
   (`1790506141836`). Future migrations generated by drizzle-kit carry real clock stamps and
   therefore sort after 0012.
2. **The migration runner repairs bookkeeping before migrating.** `scripts/migrate.cjs` (the
   container entrypoint's runner) and the dev-server open path (`applyMigrations`) first re-date
   any `__drizzle_migrations` row whose recorded stamp no longer matches the journal, matched by
   content hash (sha256 of the `.sql` file — the same value drizzle stores). Rows that already
   agree are untouched; the repair never writes application data. On an upgraded database it logs
   `[migrate-repair] re-dated 0011_schedule_excluded_months: 1790600000000 -> 1790504000000` and
   then applies 0012 normally. This also converges databases created fresh by v0.23.0, whose 0011
   row still carried the old future stamp and would otherwise have made the migrator re-apply 0012
   and fail with "duplicate column name".
3. **Regression tests for the real upgrade path** (`tests/migrate-upgrade.test.ts`): a
   v0.22.1-era database (0011 at the old stamp) is built and upgraded through the actual
   production runner; a fresh-v0.23.0 database and a brand-new install are covered too, plus a
   parity test proving the production (CJS) and dev (TS) repair implementations agree.
   `tests/migrate-journal.test.ts` permanently guards the journal: stamps strictly increasing,
   never in the future. Both would have failed `npm test` before v0.23.0 shipped.
4. **The upgrade path is now smoke-tested in Docker before anything is published.** CI's Docker
   job upgrades the most recently published release image to the build under test, and the Publish
   workflow upgrades the two most recent published images, on the same volume; the upgraded
   container must come up healthy with every journal entry applied exactly once at the journal's
   stamp. This check would have refused to publish v0.23.0.
5. **The Publish workflow now creates the GitHub release itself**, from the checked-in notes
   document plus the verified facts (date, merge commit, image tags, digest, run link). Releasing
   no longer requires any post-merge session work: the Arena session ends when the release PR
   merges. See the reworked [`RELEASE_PROCESS.md`](RELEASE_PROCESS.md) and decision 173. This
   release's GitHub page was therefore generated by the workflow, and the verified facts above
   were prepended automatically.

## Who is affected and what to do

- **Updated from v0.20.0–v0.22.1 to v0.23.0 and seeing the error:** your data is intact. Take a
  backup, then Force Update to pick up v0.23.1. The badge should read `v0.23.1 · pre-release` and
  Accounts & Pots should open normally again.
- **Fresh install of v0.23.0 (created with empty `/data`):** working, but update anyway — this
  release also re-dates the stale 0011 bookkeeping row your database carries.
- **Still on v0.22.1 or earlier:** update straight to v0.23.1. Skipping v0.23.0 is fine — that is
  exactly the upgrade the repair handles.
- **Do not** add the missing columns by hand with a SQLite tool: that produces a half-migrated
  state (columns present, journal row absent) the migrator would then reject with "duplicate
  column name" when applying 0012.

## Schema and data

No schema beyond v0.23.0's own migration `0012` (five optional per-pot credit-card columns, added
by this release's upgrade path on affected installs). The only rows this release writes are
`__drizzle_migrations` bookkeeping rows (the re-date and the record of 0012 applying). No ledger,
pot, schedule, document or setting row is touched.

## Updating in Unraid

1. **Take a backup:** Settings → Backup, or stop the container and back up
   `/mnt/user/appdata/simple-finance` consistently. Keep it outside the container.
2. **Force Update** Simple Finance. The template tracks `ghcr.io/dougalbob/simple-finance:latest`;
   if the container is pinned to a version tag, switch it to
   `ghcr.io/dougalbob/simple-finance:v0.23.1` or `:latest` first — a pin will not pick up the new
   image.

After updating, the navigation badge should read **v0.23.1 · pre-release** and the first start's
log should show the `[migrate-repair]` line followed by `[migrate] database is up to date`.
